# Add codiv.ai as a builtin OpenAI-compatible provider

## Verdict

Yes — codiv.ai can be served under an OpenAI-ish contract with **zero adapter code**. Their docs confirm a native OpenAI-compatible endpoint at `POST https://api.codiv.ai/v1/chat/completions` (Bearer auth, standard `choices`/`usage` response, SSE streaming with usage in the final chunk, function `tools` + `tool_choice`, OpenAI-shaped errors). So the "conversion" is exactly the repo's established pattern: **one registry row** (`src/provider-registry.ts` describes itself as "Adding a builtin is still ONE table row here and nothing else"), plus the two typed companion edits and tests. Bonus for "our users out there": because `src/serve.ts` exposes the whole registry as an OpenAI-compatible HTTP server, the same row automatically makes `codiv:diffusiongemma-26b` available to any OpenAI client pointed at `codewhip serve`.

## What codiv.ai is

Free public inference host for open "System One" models. Two APIs, same host and Bearer key:
1. `POST /v1/chat/completions` — OpenAI-compatible text generation, model id **`diffusiongemma-26b`** (DiffusionGemma 26B, diffusion LM). This is what codewhip uses.
2. `POST /v1/systemone` — Jev-compatible typed-questions API (noul/choice/score with probability distributions). **Not** OpenAI-shaped, but it needs no conversion for this task and is out of scope (possible future use: router classification).
Free tier: no card, 100M input + 10M text-gen tokens, 600 req/min, keys shaped `sk-codiv-…`.

## Compatibility mapping (docs → codewhip adapter)

- Request body codewhip sends (`model, messages, tools, stream, stream_options:{include_usage:true}` — `src/provider.ts:480-487`): all supported; codiv also accepts `max_completion_tokens` alias and ignores sampling params we never send.
- Streaming: SSE with usage on the last chunk before `[DONE]` — handled by `foldSseChunk`; if `stream_options` were rejected with 400/422, the existing `streamUnsupported` fallback in `openAiPort` covers it (verify live).
- Tool calls: supported (`auto`/`none`/named) → the loop's tool-calling works.
- Errors: OpenAI-shaped (`invalid_request_error`, `auth`, `rate_limit_error`/`insufficient_quota`, `overloaded_error` 529 with `retry-after`) → `httpFailure()` classification already handles these; 529 falls in the ≥500 server/retryable bucket.
- Non-standard extras (`message.reasoning` when thinking mode on, `chat_template_kwargs`) are additive fields codewhip simply ignores — non-breaking.
- Unknowns to verify live: `GET /v1/models` support, context window (docs don't state it → leave `contextWindow` unset; compaction ceiling defaults to 60k until verified).
