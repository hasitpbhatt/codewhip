## What went wrong (diagnosis)

`%APPDATA%\codewhip\provider-analytics.jsonl` shows 15 successful `meta/muse-glimmer-30b` calls with latency climbing 4s → 99.8s, then call #16 aborted at exactly **120018ms** — codewhip's own `DEFAULT_CHAT_TIMEOUT_MS`, not NVIDIA.

`src/provider.ts:755` aborts with a custom reason:
```ts
const timer = setTimeout(() => ctrl.abort(new Error("timeout")), limit);
```
Node's `fetch` rejects with that reason object, so `err.name === "Error"`. The classifier at `provider.ts:790-794` only matches `"TimeoutError"`/`"AbortError"`, so it fell into the generic branch: `network error on https://integrate.api.nvidia.com: timeout` is codewhip printing its own abort text, and it returned `retryable: "other"`. `loop.ts:307-309` treats `"other"` as terminal, so no `--models` rotation, no `--failover`/`--free` hop, no actionable hint — and the call was logged as outcome `network`, poisoning `codewhip stats`.

The test at `provider.test.ts:126-140` passes only because it stubs `{ name: "AbortError" }`, a shape real `fetch` never returns for `abort(reason)`. Repo idiom for this already exists: `loop.ts:144-153` (`withTimeout`) uses a `timedOut` flag, not name sniffing.

The call got slow because: free-tier NVIDIA + an uncatalogued 30B model, the full transcript re-sent every turn, and the model burning turns without editing — four overlapping searches, a directory read, and **six identical reads of the same 79-line file**, each repeat appending output to a prompt every later call re-sends. `argsHash` is computed at `loop.ts:399` but only used for audit.

## Plan (four stages, each independently shippable)

### Stage 1 — Fix timeout classification — `src/provider.ts`, `src/provider.test.ts`
- Replace the abort reason with a local `timedOut` flag, mirroring `withTimeout` (`loop.ts:144-153`): `setTimeout(() => { timedOut = true; ctrl.abort(); }, limit)`.
- Classify in **both** catch blocks, in order: `timedOut` → `${brand} api timed out after ${limit}ms`, `retryable: "timeout"`, analytics outcome `timeout`; then caller `signal.aborted` → `cancelled`; then keep the `TimeoutError`/`AbortError` name checks as a secondary net; then the honest network error.
- Effect: `loop.ts:307` routes it to rotation/failover, the purpose-built hint at `loop.ts:365-366` finally prints, stats stop mislabelling.
- Tests: make the stubs signal-cooperative and reject with `init.signal.reason` (real fetch semantics) instead of a fabricated `AbortError`; assert `retryable: "timeout"`. Add a pre-aborted caller signal → `cancelled`, and a generic `Error` rejection → `network`/`other` (guards against over-classifying).

### Stage 2 — Raise the `--timeout-ms` ceiling — `src/index.ts`, `src/custom-providers.ts`
- Widen validation from `5000..120000` to `5000..600000` in both places, update the error strings and the `--timeout-ms` help line (`index.ts:68`). Default stays 120s.
- Rationale: the ceiling currently equals the default, so a 60–100s free endpoint cannot be given headroom at all.

### Stage 3 — Guard repeated tool calls — `src/loop.ts`, `src/loop.test.ts`
- Memo idempotent tools (`read`, `search`, `webfetch`) by the existing `argsHash`, invalidated by a mutation-generation counter bumped on successful `edit`/`write` (so a legitimate re-read after an edit still executes).
- On an identical repeat: skip execution, emit a visible line, push the cached output with a repeat marker, audit as `loop:repeat-call`. After 3 identical repeats of one hash, replace the output with a nudge saying the result cannot change and to edit/answer instead.
- Denials are deliberately **not** cached — within a run a user `a` answer promotes a shape to remembered, and a cached denial would wrongly block it.
- Report the repeat count in `LoopResult` and print it in the run summary so the waste is visible.
- Tests: 4 identical reads → tool executes once and the nudge appears; an intervening edit invalidates the memo.

### Stage 4 — Stream responses — `src/provider.ts`, `src/provider-port.ts`, `src/index.ts`
- Send `stream: true` with `stream_options: { include_usage: true }`; parse SSE from `res.body` with a line buffer, appending `delta.content` and merging `delta.tool_calls` by `index` (concatenating `arguments`). Accept `message`-shaped chunks too, for gateways that don't use deltas.
- Timeouts: `limit` bounds time-to-first-byte; once the first chunk lands, switch to an idle timeout (no bytes for ~45s) so a slow-but-alive model isn't killed by total wall clock. Both paths route through the Stage-1 flag, with a distinct "stalled" message.
- Usage: take the final chunk's `usage`; when a provider omits it, estimate chars/4 over the assembled text and args and mark that bucket estimated, so the receipt prints `est.` rather than a fiction. Receipts keep printing either way (AGENTS.md rule 3).
- Fallback: if a provider 400/422s on streaming or returns a non-SSE body, retry that call once non-streaming and memoize non-streaming for that provider for the rest of the run (one log line, analytics outcome recorded).
- `--no-stream` escape hatch to force the old non-streaming path (help + CHANGELOG).
- Ctrl-C cancels the reader; classification via the caller signal, not the error name.
- Tests: SSE parser units (content deltas, a tool call split across chunks, a usage chunk, `[DONE]`, malformed lines), an idle-timeout case, and a non-SSE fallback case via a stubbed fetch returning a `ReadableStream`.

### Docs + verification
- `CHANGELOG.md`: correct line 16 (it claims timeouts already join rotation) and add entries for the ceiling, the repeat guard, and streaming. `docs/roadmap.md`: the guard lands under "Truth to model"; streaming under the H2 provider-matrix/latency line.
- Per stage: `npm run lint`, `npm run typecheck`, `npm run build`, `npm test` all green.
- End-to-end check: rerun the original command with `--timeout-ms 600000`, and with a bogus short timeout to confirm a real timeout now prints "retry with --models … or --timeout-ms" instead of a bogus network error and is recorded as `timeout` in `codewhip stats`.

Stages ship in order 1 → 2 → 3 → 4; Stage 1 is small and unblocks everything else, Stage 4 is the only one that touches receipt accounting and carries provider-compatibility risk, which is why it lands last with its own tests.
