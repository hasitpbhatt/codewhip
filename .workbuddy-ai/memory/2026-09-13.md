## 1min.ai assessment (same day, follow-up) — decision pending

User asked to integrate `1min.ai`, framing it as "doesn't use v1, we can
translate the mapping". Research says the framing undersells it — this is a
**bidirectional schema translation with a capability gap**, not a path rename.
No code written; awaiting the user's call.

**Evidence that it isn't a path rename:** three independent OpenAI-shape bridge
projects exist for exactly this (`maerzlc/1min-proxy`, `binuengoor/1min-bridge`,
`kokofixcomputers/1min-relay`) plus a blog writeup. Nobody builds a Go project
to rename a path.

**The actual deltas (from `docs.1min.ai`):**
- `POST /api/chat-with-ai?isStreaming=true` — no `/v1/chat/completions`
- `API-KEY: <key>` header, not `Authorization: Bearer` (intro page claims Bearer;
  the chat-endpoint page contradicts it — the proxy translates, so trust `API-KEY`)
- required discriminator `type: "UNIFY_CHAT_WITH_AI"`
- **no `messages[]`** — `promptObject.prompt` (one string) + server-side
  `conversationId`; history must be flattened into the prompt with role labels
- **no `tools` / `tool_choice`** — see blocker below
- no sampling params (`temperature`, `max_tokens`) documented
- response `aiRecord.aiRecordDetail.resultObject[]` (array of strings), not
  `choices[0].message.content`
- **no `usage` block** → `promptTokens`/`completionTokens` can only be estimated,
  so `ChatPortResult.usageEstimated: true` and receipts print "est."
- errors `{success:false, error:{code,message}}`
- SSE is **named events** (`event: content` / `result` / `done` / `error`) with
  flat `data:{"content":"..."}`, not `data:{choices:[{delta}]}` + `[DONE]`
- model listing is `GET /models?feature=...`, not `/v1/models`

**The blocker:** no **native** tool calling. `1min-proxy`'s own README: "Tool
calling is emulated — tool definitions are injected into the prompt and responses
are parsed for JSON tool call structures. This is best-effort and depends on model
cooperation." A text-only port gives a provider that answers but cannot act —
structurally the `codestral-latest` failure mode the README already warns about.
Prompt-injected tool emulation would work "best effort", which sits badly with
this project's "the meter never lies" wedge.

**Also:** it is credit/subscription-based (`teamUser.creditLimit`/`usedCredit`),
so under the `--free` invariant it must NOT join `FREE_CHAIN`. `--provider` only.

**Scope if built natively:** a new port, not a table row. `makePort` and
`makePortForConfig` both currently just `return openAiPort(...)` with no adapter
keying, so it needs a `cfg.id` branch (or a port discriminator on
`ProviderConfig`), a custom named-event SSE reader, a message flattener, a
response translator, and an error mapper — ~400 LOC + tests, against AGENTS.md's
"<150 lines per tool" and "no new runtime dep without justification".

**Recommended alternative:** don't write 1min-specific code. Run a self-hosted
bridge and register it as a **custom provider**. That is blocked by exactly one
guard: `custom-providers.ts` requires `https://` in BOTH `normalize()` (line 43)
and `isValidRecord()` (line 74), so a loopback `http://` custom is dropped on
write *and* on load. Relaxing that one guard to accept loopback `http://` unlocks
this AND the long-standing local-runtime gap (Ollama `:11434` / vLLM `:8000`) AND
the router's dead `private → local` route. One change, three unblocks.

**Correction (same day, after the user pushed back): the bridge recommendation
does NOT avoid hosting.** Verified against `binuengoor/1min-bridge`'s README:
**no publicly hosted instance exists** — the project is explicitly "self-hosted
and edge-native", and every user must run their own. Two supported paths, both
of which are things you operate:
  - Docker/Node container: `docker run -d -p 3000:3000 -e ONE_MIN_API_KEY=… \
    ghcr.io/binuengoor/1min-bridge:latest` — a live process on every run.
  - Cloudflare Workers: `npx wrangler secret put ONE_MIN_API_KEY && npx wrangler
    deploy` — real hosting, your account, your key in their secret store.
There is no third option where you point at someone else's instance, because
that means handing your 1min API key to a stranger — strictly worse for a
project whose wedge is trust.

So the honest trade is **~400 LOC of one-time codewhip code vs a permanent
operational dependency**. The bridge also costs: availability coupling (bridge
down → run fails), maintenance lag (1min API change → wait on a third party or
fork), split debuggability (codewhip sees only translated output, so it cannot
tell "1min returned garbage" from "bridge bug"), and a metering number it
cannot verify. The recommendation was optimising for codewhip's code cleanliness
and externalising the cost onto the operator. Given "I don't want to host
anything", the user's original pick — the native adapter — is the right one.
Recorded so the same wrong recommendation isn't re-derived.

## Product-surface audit + safety-classifier fix (same day, follow-up)

User asked whether everything in codewhip is actually usable together. Audited
by running the built CLI, not by reading docs. Verified working end-to-end:
51 builtins listed, `--free` live run succeeded keyless (kilo → real 1052+37
tokens, $0.0000 `:free`), `--plan`, `--class private --provider llm7` override,
`provider add`/`remove` round trip, `models llm7` (keyless listing, 47 models),
`demo --deny` (5 blocks, chain INTACT), `trust`, `metrics`, `audit --verify`,
`policy candidates`, `remember list`, `pack list`, `agents`, `rollback`,
`auth status`. 5 keyless providers: kilo, opencode, empero, pollinations, llm7.

**FIXED — safety-classifier dead alternative in `src/router.ts`.** `PRIVATE_RX`
wrapped `.env` inside an outer `\b(...)\b` group, i.e. `\b\.env\b`. A `\b` can
never match immediately before a literal `.`, so that alternative only fired
when the dot was glued to a preceding word char (`foo.env`) and silently missed
every ordinary phrasing. Measured before the fix:

    implement | read the .env file and summarize it     <-- routed to CLOUD
    implement | .env is missing, recreate it            <-- routed to CLOUD
    implement | the .env file has a bad value           <-- routed to CLOUD
    private   | check foo.env for stale vars            <-- only this one worked

So the class whose entire job is "refuse cloud routing for secret-touching
prompts" was passing the most common `.env` phrasings straight to a free cloud
tier. Fixed by hoisting `.env` out of the `\b` group: `...|\.env\b` as its own
alternative, which allows any preceding character. All four phrasings now
classify `private`. Regression test added: `router.test.ts` "catches .env in
the ordinary phrasings, not just word-glued (regression 2026-09-13)".

Note the existing test `classify("rotate the api key in .env")` "covered" .env
but actually matched the `api key` alternative — which is why the dead branch
survived. Lesson: a test whose assertion passes via a *different* alternative
proves nothing about the branch it looks like it covers.

Verified: lint clean, typecheck clean, build clean, `npm test` **287/287 pass**.

**FOUND, not fixed (needs a decision):**
1. `ppio` has `envVar: "PIO_API_KEY"` — missing a P. Only outlier of 51 (scanned
   id-vs-envVar programmatically). `brand` is "ppio" and the free-chain entry
   says "PPIO free trial credits", so it reads as a typo. Left alone because
   env var names are a documented public contract (help text) — renaming is a
   breaking change that should be deliberate.
2. `--class private` cannot be routed: `routeFor("private")` returns an error by
   design. Combined with (now-fixed) #above this was worse than it looked, but
   even correct classification means `.env` prompts hard-fail unless the user
   passes `--provider`. The refusal is intentional; the *frequency* of hitting

3. 18 new `defaultModel` slugs remain catalog-derived, not live-probed (needs

4. Doc drift: `docs/moat/01-leverage.md:39` calls it "a 5-line classifier

## `serve` shutdown leak — MaxListenersExceededWarning (same day, follow-up)

User reported: `MaxListenersExceededWarning: Possible EventEmitter memory leak
detected. 11 close listeners added to [Server].`

**Reproduced exactly**, in-process: `server.close(cb)` adds a 'close' listener
per call, so 12 calls → 12 listeners → warning on the 11th. Verified that the
request path is innocent first (15 GETs + 15 POSTs left the server at
`request:1 connection:1 listening:1`), and that `serve.ts` is the only
`createServer` in the repo — which left exactly one caller: my signal handler.

**Two defects, one symptom.** The handler called `server.close()` on *every*
SIGINT, and:
1. `close()` is not idempotent → one leaked listener per keypress.
2. `close()` waits for existing connections, and an idle HTTP keep-alive socket
   has no natural end → the process never exits → the operator presses Ctrl-C
   again → defect 1 fires. **The warning was a symptom of the hang, not a
   separate bug.**

**Fix:** `createShutdown(server, exit, graceMs)` in `src/serve.ts` — one
idempotent controller. First call: `close()` + `closeIdleConnections()` + an
unref'd 5s force-exit timer. Second call: immediate exit ("operator is
impatient") instead of stacking another listener. `cmdServe` registers it once
for SIGINT and SIGTERM and prints "press Ctrl-C again to force".

Also added while there: `server.on("error")` so `EADDRINUSE` prints
`port N is already in use — pick another with --port` instead of an unhandled
'error' event and a raw stack trace. Verified live with two servers on 8906.

Two regression tests in `serve.test.ts`: listener count stays at 1 across 12
shutdown calls, and an idle keep-alive socket is actually dropped so the close
callback fires. lint/typecheck/build clean, `npm test` **342/342 pass**.

**Transferable lesson:** for any long-lived server, `close()` is not
idempotent and keep-alive sockets block it. An "EventEmitter memory leak"
warning on a `[Server]` usually means the process is failing to exit and
someone is retrying — look for the hang, not just the listener.

## Can `codewhip serve` run on Cloudflare Workers? (same day, follow-up)

User asked. Answer: **not as written, but the gap is ~60 lines of entry point,
not a rewrite.** No code written; assessment only.

**Cloudflare added `node:http` SERVER support in Sept 2025** — this is new
enough that it invalidates any older "Workers can't run an http server" prior.
Gated by `enable_nodejs_http_server_modules` on top of `nodejs_compat`;
auto-enabled at compatibility date ≥ `2025-09-01`. Wiring is
`httpServerHandler` from `cloudflare:node`:
`export default httpServerHandler(server)` (auto-calls listen) or
`httpServerHandler({port: 8080})`, or `handleAsNodeRequest(port, request)` for
full control of the fetch handler.

**Portable as-is:** `openAiPort` / `oneminPort` (plain fetch), the registry,
`res.write()` streaming → the synthetic-SSE design survives. `'socket'` /
`'upgrade'` unsupported but unused. `node:fs` exists as an EMPTY in-memory FS
and every read in this repo is already try/catch'd (`auth.ts:144`,
`provider-stats.ts:44`), so nothing throws — but `credentials.json` can never
be populated, so keys MUST come from Worker secrets/env. That is the correct
design there anyway.

**Blockers, line-level:**
1. `serve.ts:453` `server.listen(opts.port, opts.host, cb)` — Workers supports
   only `listen()` / `listen(0, cb)` / `listen(cb)`. No host argument, and the
   port is a *routing key*, not a socket.
2. `serve.ts:428` `server.closeIdleConnections()` — **explicitly not
   implemented** (`closeAllConnections()` too). So the shutdown fix shipped
   earlier today is the single most Cloudflare-hostile line in the repo.
3. `process.on("SIGINT"/"SIGTERM")` + `process.exitCode` in `cmdServe` — no
   process model, no signals.
4. `isLoopback(host)` / `--token` refusal — meaningless with no bind step.
5. `connection: keep-alive` (serve.ts:364) is ignored; keep-alive unsupported.

**The real answer is not technical.** `serve` is loopback-by-default precisely
because it spends the user's keys for whoever can reach the port (serve.ts:22).
A Worker has a public URL, so that reasoning inverts: one shared token, no rate
limit, no per-caller quota, no spend cap. Two different asks hide behind "host
it on Cloudflare": (a) *private reachability* and (b) *a public gateway*.

**For (a) do not port anything** — `cloudflared tunnel --url
http://127.0.0.1:8899` fronts the loopback server with zero code changes,
keeping `--token`, the loopback bind, and the whole posture. Strictly better
than a Workers port for that goal. (b) is a product decision (rate limiting,
per-caller auth, spend cap, and who pays) and belongs in `docs/moat/` as a
recorded ruling before any code.

### A 5xx killed the run instead of rotating (real defect, live trigger)
Found while checking whether the `--free` chain survives empero's maintenance
window. It does not, and the reason is general:

```ts
const retryable = status === 429 ? "rate-limited" : status === 401 || status === 403 ? "auth" : "other";
```

Everything else — **500, 502, 503** — fell into `"other"`, and the loop gate only
rotates on `"rate-limited"`/`"timeout"`. Verified by stubbing fetch and printing
the classification for each status. So a provider in a maintenance window ends the
run instead of hopping to the next free tier — the chain failing at exactly the
thing it exists to survive.

Fixed by adding a `"server"` class (5xx + 408) to `RetryableKind` and including it
in the rotation gate. Chose a new class over reusing `"timeout"` so messages and
status codes stay honest (`server error`, and `serve.ts` maps it to 502 rather
than 504). Classified in BOTH adapters (`provider.ts` `httpFailure`, `onemin.ts`);
4xx deliberately stays terminal, since a bad request repeats wherever it is sent.
Updated the `--models`/`--failover`/`--free` help and banners from
"rate-limit/timeout" to "rate-limit/timeout/5xx" so the docs match the behaviour.
+5 tests (362 total).

### My verification harness was lying
`npm run <script> | tail -N` hides failures two ways: the pipe makes the exit code
`tail`'s (always 0, so `&&` chains sail past a failing gate), and because npm's
banner is block-buffered on a pipe while tsc's stderr is unbuffered, the errors
flush FIRST and `tail` shows only the banner. Both tsc (TS1117) and oxlint
(`no-dupe-keys`) had been flagging a duplicated `hcnsec` key in
`FIELD_BY_PROVIDER` — I introduced it in an earlier interrupted edit and never saw
it, because I was reading a truncated tail. Lesson: run gates bare with
`; echo $?`, or redirect to a file and read it. Never trust a piped tail.
(Also: parallel edits to one file visibly dropped a write here — read the file
back after a batch.)
